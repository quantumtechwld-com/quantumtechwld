Endpoints do Fluxo Financeiro

PATCH
/api/orders/[id]
Admin envia proposta — define estimatedValue, downPaymentPct, method. Cria/substitui OrderFinancial e parcelas. Avança status para PROPOSAL_SENT.
POST
/api/orders/[id]/checkout
Cliente inicia pagamento Stripe. Busca parcela STRIPE pendente, inclui installmentId no metadata. Em modo mock, actualiza OrderFinancial imediatamente.
POST
/api/webhooks/stripe
Recebe checkout.session.completed. Se metadata contém installmentId → chama handleInstallmentPaid (marca PAID, recalcula paidCents, avança Order para IN_PRODUCTION na 1.ª parcela).
PATCH
/api/admin/financial/[orderId]/installments/[id]
Admin confirma pagamento manual. Action: confirm_manual. Marca parcela PAID, recalcula paidCents, avança Order para IN_PRODUCTION se sequência 1.
GET
/portal/orders/[id]
Página do cliente. Mostra PayOrderButton (Stripe) ou card informativo (Manual) para parcelas PENDING. Query inclui financial { installments }.
GET
/admin/financeiro/[orderId]
Backoffice financeiro. Mostra resumo, barra de progresso e botões de confirmação manual por parcela.

Bugs Corrigidos — Auditoria 22/04/2026

B1 — checkout/route.ts · metadata incompleto
installmentId nunca era enviado ao Stripe → handleInstallmentPaid nunca era chamado
O checkout criava a sessão Stripe com apenas metadata: { orderId }. O webhook verificava session.metadata?.installmentId — como estava sempre undefined, caia no caminho legacy (Payment model) e o OrderFinancial permanecia PENDING para sempre.

Fix: antes de criar a sessão, busca a parcela STRIPE PENDING em OrderFinancial e inclui installmentId no metadata quando existe.
B2 — checkout/route.ts · modo mock ignorava OrderFinancial
Mock payment não actualizava OrderFinancial nem PaymentInstallment
Em modo desenvolvimento (STRIPE_SECRET_KEY ausente), o checkout fazia upsert do modelo Payment e avançava o pedido para IN_PRODUCTION, mas ignorava completamente OrderFinancial e PaymentInstallment. O portal continuava a mostrar o botão de pagamento indefinidamente.

Fix: quando existe stripeInstallment, o caminho mock agora actualiza PaymentInstallment.status = PAID e OrderFinancial.paidCents / status = PAID imediatamente.
B3 — webhooks/stripe/route.ts · lógica morta em handleInstallmentPaid
Condição paid.length === 0 nunca era verdadeira após pagamento
O array paid é recalculado depois de o installment já ter sido marcado PAID, portanto paid.length é sempre ≥ 1 após o primeiro pagamento. A condição if (paid.length === 0) para avançar o pedido para IN_PRODUCTION nunca disparava neste caminho.

Fix: alterado para if (paid.length === 1) — exactamente quando a primeira parcela acaba de ser paga.
B4 — tests/components/AdminOrdersPage.test.tsx · mocks incompletos (pré-existente)
db.user.findMany e useRouter não estavam mockados
Após adicionar o ClientFilter (commit 5399fe6), o componente passou a chamar db.user.findMany e useRouter(), mas os mocks do ficheiro de teste não incluíam essas dependências.

Fix: adicionado userFindMany ao mock do Prisma e mocks completos de useRouter, useSearchParams, usePathname ao mock de next/navigation.

Retrocompatibilidade

ℹ
Pedidos sem OrderFinancial continuam a funcionar via modelo Payment legado. O webhook verifica metadata.installmentId — se ausente, actualiza apenas Payment. O portal mostra o link de fatura se order.financial?.status === "PAID" ou order.payment?.status === "PAID". Nenhuma migração de dados é necessária.
